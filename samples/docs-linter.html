Когда правила документации пора превращать в код

Как повторяющиеся замечания ревью стали Python-линтером — и почему автоматизировать стоит далеко не всё

Контекст: продуктовая база знаний в docs-as-code, где статьи проходят редакторское ревью и собираются вместе с фронтендом.

Моя роль: написал Python-линтер и дополнил существующий командный skill правилами для ссылок, callout-блоков, скриншотов и стиля обращения к читателю с помощью Claude Code.

Масштаб решения: 13 правил, один Python-файл без внешних зависимостей, разделение находок на ERROR и WARN.

У документационной команды довольно быстро появляется собственный набор маленьких правил.

Не оставлять .md во внутренних ссылках. Не оформлять предупреждение обычной цитатой. Проверять, что изображение действительно существует. Не использовать повелительное Click там, где статья должна быть описательной.

По отдельности всё это выглядит слишком мелким для отдельного инструмента. Проще заметить на ревью и поправить.

На одном-двух ревью это почти не мешает. Но когда одинаковая правка повторяется из статьи в статью, часть редакторской работы перестаёт быть редактурой. Перед нами уже повторяемая проверка с однозначным ответом.

Если человек несколько раз исправляет одну и ту же вещь, а правильность можно определить формально, возможно, это уже задача для кода.

От замечаний ревью к правилам линтера

До появления линтера похожие ошибки уже исправлялись руками: сломанные пути к изображениям, курсив в местах, где ожидался другой стиль, ссылки с .md, жёстко прописанные абсолютные адреса базы знаний, некорректно оформленные callout-блоки и команды вроде Click в reference-контенте.

Вместо того чтобы каждый раз надеяться на внимательность автора или редактора, мы выделили механические случаи в отдельный скрипт. В итоге получился небольшой линтер на стандартной библиотеке Python.

ГруппаПример проверкиУровень
Изображениясуществует ли файл; корректен ли абсолютный путьERROR
Ссылкисуществует ли целевая статья; не остался ли .mdERROR
Оформлениене выглядит ли обычный blockquote как callout; нет ли нежелательного курсиваWARN
Голосyou и Click в типах статей, где они нежелательныWARN

Всего таких правил стало тринадцать: пять дают ERROR, восемь — WARN. Но число само по себе не так важно. Важнее граница: линтер не пытается определить, хорошая ли статья. Он не решает, понятен ли текст, правильно ли выбран тип Diátaxis или действительно ли конкретный раздел полезен читателю.

Он отвечает только на вопросы, для которых можно получить воспроизводимый результат.

Почему не всё нарушение должно ломать проверку

На следующем шаге возник менее очевидный вопрос: что делать, когда правило сработало?

Сломанный путь к картинке почти наверняка означает реальный дефект. Если файл не существует, на опубликованной странице будет пустое место. Здесь логично вернуть ERROR и ненулевой exit code.

Со стилистическими правилами всё сложнее. Например, слово you может быть нежелательным в reference-статье, но конкретный контекст всё равно может оказаться оправданным. Автоматически блокировать работу из-за каждого такого случая — значит быстро получить инструмент, который команда начнёт обходить.

Поэтому появился второй уровень:

ERROR → система уже знает, что результат неправильный
WARN  → система знает, что это место нужно проверить

ERROR должен быть исправлен. С WARN решение остаётся за человеком: изменить текст или явно оставить срабатывание с объяснением.

Хороший линтер не обязательно должен находить всё. Гораздо важнее, чтобы его строгим сигналам доверяли.

Одно правило от входного текста до результата

Особенно легко получить ложные срабатывания на правилах голоса. Допустим, мы хотим находить Click в reference-материалах. Наивный поиск слова по всему Markdown быстро начнёт ругаться на примеры кода:

Run the command:
Click

Expected output: ...

Для читателя это кодовый фрагмент, а не инструкция «нажмите». Значит, перед проверкой нужно отделить основной текст статьи от конструкций, которые не должны участвовать в этой проверке.

В линтере подготовка текста стала отдельным шагом: пропускается frontmatter, блоки кода и HTML-комментарии; для обычной строки сохраняются две версии. Первая нужна для разбора ссылок и изображений. Во второй простой regex вырезает inline-code-фрагменты в одинарных бэктиках — именно по этой версии работают правила голоса.

Концептуально это выглядит так:

Markdown line
   ↓
raw ─────────→ links / images
   ↓
remove simple inline code
   ↓
prose ───────→ voice / style rules

Поэтому Click в обычном предложении может дать предупреждение, а то же слово внутри простого inline-code-фрагмента в одинарных бэктиках — нет.

Ниже — сокращённый фрагмент из реального kb_lint.py. Я убрал строки, не относящиеся к этому правилу, но сама логика проверки не изменена:

RE_CLICK = re.compile(r"(^|[.!?:]\s+|^\s*(?:\d+\.|[-*+])\s+)(Click|Double-click|Right-click)\b")
RE_INLINE_CODE = re.compile(r"`[^`]*`")

# article_lines(...)
yield n + 1, raw, RE_INLINE_CODE.sub("", raw)

# lint_file(...)
body = RE_URL.sub("", prose)

if atype in ("reference", "explanation"):
    if RE_CLICK.search(body.lstrip("> ")):
        F.append(Finding(
            rel, n, "WARN", "click",
            f'imperative "Click" in a {atype} article; say what the element does ("The name links to…")',
            s
        ))

Регулярное выражение ищет императивный Click, но получает уже очищенную версию строки: простые inline-code-фрагменты в одинарных бэктиках вырезаются раньше. Это не полноценный Markdown-парсер, а узкая эвристика, достаточная для этого правила.

Чтобы не публиковать внутренний документ, ниже — реальный запуск текущего скрипта на синтетическом Markdown-файле. В нём обычная строка Click Save to continue. должна дать предупреждение, а `Click` внутри inline-code — быть проигнорирован.

$ python .claude/skills/kb-diataxis-frontmatter/scripts/kb_lint.py \
    docs/reference-demo.md --type reference --rules click

# docs/reference-demo.md  (type: reference)

docs/reference-demo.md:7  WARN   click           imperative "Click" in a reference article; say what the element does ("The name links to…")  | Click Save to continue.

1 article(s), 0 error(s), 1 warning(s)

Команда завершается успешно: WARN не даёт ненулевой exit code. Это намеренно — скрипт сообщает, что место требует проверки, но не утверждает, что текст автоматически неверен.

На практике «давайте просто проверим регулярным выражением» оказалось только первой версией решения. Чтобы правило стало полезным, пришлось учитывать структуру документа и цену ложных срабатываний.

Тип статьи тоже влияет на проверку

Правила you и Click зависят от типа материала. Для how-to повелительная форма естественна. Для reference или explanation — уже нет.

Сам скрипт не пытается заново классифицировать содержание статьи. Он использует дешёвый сигнал — префикс имени файла. Если имя начинается с how-to-, тип считается how-to; если с tutorial- — tutorial; всё остальное по умолчанию считается reference. При необходимости тип, включая explanation, можно задать явно через --type.

Это заведомо несовершенная эвристика. Поэтому предполагаемый тип явно выводится в отчёте и при необходимости переопределяется параметром --type. Семантическую классификацию всё равно выполняет человек или LLM по содержанию статьи.

Здесь линтер снова не пытается стать умнее, чем нужно. Он берёт доступный формальный сигнал и оставляет возможность исправить его, если контекст говорит обратное.

Сироты — ещё один пример осторожной автоматизации

Скрипт умеет находить изображения, которые больше нигде не используются. На первый взгляд это идеальный кандидат на автоматическое удаление.

Но в docs-as-code текущая ветка не всегда содержит весь контекст. Файл может быть подготовлен для статьи из другого PR или использоваться фронтендом, конфигом либо главной страницей.

Поэтому неиспользуемое изображение — только WARN. Линтер расширяет область поиска за пределы Markdown, но окончательное решение об удалении оставляет человеку.

Для меня здесь работает более осторожный принцип: лучше автоматизировать обнаружение, чем необратимое действие.

Как линтер встроен в workflow

В основном skill линтер — отдельный механический этап AI-assisted workflow: инструкция предписывает Claude Code запускать его при проверке статьи. Workflow подготовки скриншотов тоже заканчивается запуском того же kb_lint.py после подготовки и вставки изображения. Это именно инструкция для агента, а не автоматический вызов со стороны CI.

Линтер печатает находки в формате path:line SEVERITY rule message | excerpt. ERROR означает дефект, который нужно исправить. По каждому WARN остаётся отдельное решение: изменить текст или оставить срабатывание с объяснением.

При этом kb_lint.py не подключён напрямую к CI или hooks и не является самостоятельным CI-gate. Отдельного набора unit/integration/eval-тестов и fixtures у него тоже пока нет. Без такого набора сложнее гарантировать, что изменение одной эвристики не создаст регрессию в другом сценарии. Поэтому один из следующих шагов — автоматические тесты.

Самый полезный результат — увидеть пробелы

После появления линтера стало заметнее не только то, что мы автоматизировали, но и то, что осталось за его пределами.

Например, скрипт вообще не проверяет frontmatter. И это особенно показательно, потому что раньше уже встречалась массовая ошибка: поле keywords было записано строкой вместо массива сразу в нескольких десятках статей.

То есть у нас есть реальный класс ошибки, который уже стоил ручного исправления, но до сих пор проверяется только по текстовой инструкции.

Есть и другие ограничения:

  • правило Click ловит не все позиции слова в предложении;
  • внутренние ссылки проверяются на существование страницы, но не якоря после #;
  • тип статьи по имени файла может быть определён неверно;
  • терминология остаётся вне линтера;
  • skills предписывают Claude Code запускать скрипт как часть AI-assisted workflow, но сам kb_lint.py не подключён к CI или hooks;
  • для самого линтера пока нет отдельного набора unit/integration/eval-тестов и fixtures.

Этот список заодно показывает следующие точки развития линтера. Его ограничения по крайней мере видны явно.

Что в итоге осталось человеку

После появления линтера редактор не перестал быть нужен. Просто часть вопросов сменила владельца.

КодЧеловек / LLM
существует ли файл изображениянужно ли это изображение статье
существует ли целевая страницаправильно ли выбрана ссылка
есть ли формально нежелательная конструкцияоправдана ли она в этом контексте
соответствует ли текст механическому правилупонятен ли он читателю

Именно это оказалось для меня главным критерием автоматизации: не «можно ли написать проверку», а может ли код вынести достаточно надёжный вердикт, чтобы человек перестал каждый раз решать тот же вопрос заново.

Если ответ да — правило постепенно переезжает в линтер. Если нет — автоматизация должна максимум подсветить место, но не изображать уверенность, которой у системы нет.
