Shallow clone и одна дата Updated

Как небольшая UI-фича привела нас к Git history, hashes, generated state и особенностям CI

Дата Updated под заголовком статьи выглядит почти идеальной задачей на несколько строк кода.

Берём Markdown-файл:

git log -1

получаем дату последнего коммита и показываем её пользователю.

Локально всё действительно работает.

Проблемы начинаются, когда тот же код оказывается в другом окружении.

В нашем случае staging собирался из shallow clone. Полной истории Git там нет, поэтому вопрос «когда последний раз менялась эта статья?» неожиданно перестаёт иметь очевидный ответ. Результат git log начинает зависеть не только от файла, но и от того, сколько истории доступно конкретной сборке.

Затем выяснилась вторая проблема: не каждый коммит Markdown должен менять дату для читателя.

Если поменялся только frontmatter — например, позиция статьи в меню, — содержание осталось прежним. Нужна уже не дата последнего изменения файла, а дата последнего изменения именно его тела.

И простая UI-задача постепенно превращается в задачу хранения состояния.

Решение прошло несколько стадий: дата из Git → отдельный каталог дат → каталог, в котором рядом с датой хранится SHA-256 тела статьи. Так изменение содержимого можно определить даже там, где полной истории Git нет.

Markdown
   ↓
отделить frontmatter
   ↓
SHA-256 тела
   ↓
сравнить с сохранённым состоянием
   ↓
выбрать дату
   ↓
updatedAt

На первый взгляд такое решение намного надёжнее git log -1: состояние хранится вместе с кодом и приезжает в сборку независимо от глубины clone.

Но появляется новая проблема. Как только вычисленное состояние хранится в Git, оно само превращается в часть системы.

Каталог может конфликтовать между параллельными PR. Запись может перестать соответствовать статье. Генератор может вести себя по-разному в разных окружениях.

Одна версия решения даже была полностью откатана через 21 минуту, а на следующий день тот же патч вернулся обратно. Причина отката в истории репозитория не записана — хороший пример того, почему инженерную ретроспективу иногда приходится строить не как красивую историю, а как набор того, что действительно можно подтвердить.

В итоге вопрос изменился. Изначально он звучал как «как показать дату обновления статьи?», а стал звучать так: что в нашей системе является источником истины для утверждения, что содержание статьи изменилось такого-то числа?

И четыре строки вокруг git log перестают выглядеть очевидным решением.

Что будет в полной статье

Разберу всю эволюцию механизма: shallow clone, поиск последнего изменения тела без frontmatter, каталог generated state, SHA-256, build:updated, комбинации local/CI и clean/dirty working tree, а также отдельную кроссплатформенную проблему LF/CRLF, из-за которой одинаковый текст может получать разные hashes на Windows и в CI.
