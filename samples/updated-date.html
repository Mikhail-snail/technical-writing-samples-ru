Shallow clone и одна дата Updated

Как небольшая UI-фича привела нас к истории Git, хешам, сгенерированному состоянию и особенностям CI

Контекст: командная доработка механизма, который показывает читателю дату содержательного обновления статьи.

Моя роль: в этом кейсе я описываю и анализирую подтверждаемую эволюцию командного решения; отдельные этапы реализации не приписываю себе.

Фокус кейса: как локально простое решение меняется, когда появляются shallow clone, frontmatter и состояние, которое нужно переносить между сборками.

Дата Updated под заголовком статьи выглядит почти идеальной задачей на несколько строк кода.

Берём Markdown-файл и спрашиваем Git о последнем коммите, который его менял:

git log -1 --format=%cs -- path/to/article.md

Получаем дату и показываем её пользователю.

Локально всё действительно работает.

Но в другом окружении исходное предположение начинает рассыпаться.

В нашем случае staging собирался из shallow clone. Полной истории Git там нет, поэтому вопрос «когда последний раз менялась эта статья?» перестаёт иметь один и тот же ответ во всех окружениях. Результат зависит не только от файла, но и от того, сколько истории доступно конкретной сборке.

Появилась и вторая проблема: не каждый коммит Markdown должен менять дату для читателя.

Если изменился только frontmatter — например, позиция статьи в меню, — содержание осталось прежним. Значит, нужна уже не дата последнего изменения файла, а дата последнего изменения именно его тела.

Простая UI-задача постепенно превратилась в задачу хранения состояния.

Решение прошло несколько стадий: дата из Git → отдельный каталог дат → каталог, в котором рядом с датой хранится SHA-256 тела статьи. Так изменение содержимого можно определить даже там, где полной истории Git нет.

Markdown
   ↓
отделить frontmatter
   ↓
SHA-256 тела
   ↓
сравнить с сохранённым состоянием
   ↓
выбрать дату
   ↓
updatedAt

На первый взгляд это надёжнее прямого обращения к git log: состояние хранится вместе с кодом и приезжает в сборку независимо от глубины clone.

Но как только вычисленное состояние хранится в Git, оно само превращается в часть системы.

Каталог может конфликтовать между параллельными PR. Запись может перестать соответствовать статье. Генератор может вести себя по-разному в разных окружениях.

Одна версия решения даже была полностью откатана через 21 минуту, а на следующий день тот же патч вернулся обратно. Причина отката в истории репозитория не записана. Для меня это хороший пример того, почему инженерную ретроспективу иногда приходится строить не как красивую историю, а как набор того, что действительно можно подтвердить.

В итоге изменился сам вопрос. Изначально он звучал как «как показать дату обновления статьи?», а стал звучать так: что в нашей системе является источником истины для утверждения, что содержание статьи изменилось такого-то числа?

И несколько строк вокруг git log перестают выглядеть очевидным решением.

Что показывает этот кейс

  • Почему поведение Git-зависимой функции может измениться между local и CI.
  • Как отличить изменение metadata от изменения содержимого документа.
  • Почему вынесенное сгенерированное состояние решает одну зависимость и одновременно создаёт новые: конфликты, stale state и кроссплатформенность.
