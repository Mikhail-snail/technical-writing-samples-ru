Shallow clone и одна дата Updated

Как небольшая UI-фича привела к работе с историей Git, хешами, сгенерированным состоянием и особенностями CI

Контекст: командная доработка механизма, который показывает читателю дату содержательного обновления статьи.

Моя роль: анализировал историю изменений и собрал ретроспективу командного решения; реализацию отдельных этапов не приписываю себе.

Фокус кейса: как локально простое решение меняется, когда приходится учитывать shallow-клон, frontmatter и состояние, которое нужно переносить между сборками.

Дата Updated под заголовком статьи выглядит почти идеальной задачей на несколько строк кода.

Берем Markdown-файл и спрашиваем Git о последнем коммите, который его менял:

git log -1 --format=%cI -- path/to/article.md

Получаем дату и показываем ее пользователю.

Локально все действительно работает.

Но в другом окружении исходное предположение начинает рассыпаться.

В нашем случае staging собирался из shallow-клона. Полной истории Git там нет, поэтому вопрос «когда последний раз менялась эта статья?» перестает иметь один и тот же ответ во всех окружениях. Результат зависит не только от файла, но и от того, сколько истории доступно конкретной сборке.

Команда одна, а источник данных разный

git log -1 -- path/to/article.md ищет последний доступный коммит для этого пути в локальной истории текущего checkout. На рабочей машине это может быть длинная история репозитория, а в CI — только ее небольшой хвост. Сама команда не знает, что где-то существуют более ранние коммиты, которых нет в текущем клоне.

Поэтому проблема была не в синтаксисе git log. Проблемным оказалось исходное предположение, что Git history в любой среде можно использовать как одинаковый источник истины для пользовательской даты.

Появилась и вторая проблема: не каждый коммит Markdown должен менять дату для читателя.

Если изменился только frontmatter — например, позиция статьи в меню, — содержание осталось прежним. Значит, нужна уже не дата последнего изменения файла, а дата последнего изменения именно его тела.

Простая UI-задача постепенно превратилась в задачу хранения состояния.

Решение прошло несколько стадий: дата из Git → отдельный каталог дат → каталог, в котором рядом с датой хранится SHA-256 тела статьи. Так изменение содержимого можно определить даже там, где полной истории Git нет.

Хеш стал идентификатором состояния содержимого

SHA-256 здесь нужен не как механизм безопасности. Его задача проще: получить компактный отпечаток именно тела статьи. Если изменился только frontmatter, хеш тела остается прежним. Если меняется содержимое, меняется и отпечаток.

Markdown
   ↓
отделить frontmatter
   ↓
SHA-256 тела
   ↓
сравнить с сохраненным хешем
   ├─ совпал     → сохранить прежнюю дату
   └─ изменился  → зафиксировать новое состояние
   ↓
updatedAt

Так дата перестает вычисляться исключительно из доступной Git history. Для следующей сборки важны уже два значения из сохраненного состояния: какой отпечаток тела был известен системе и какая дата ему соответствовала.

На первый взгляд это надежнее прямого обращения к git log: состояние хранится вместе с кодом и приезжает в сборку независимо от глубины клона.

Сохраненное состояние само становится зависимостью

Но как только вычисленное состояние хранится в Git, оно само превращается в часть системы.

Теперь нужно поддерживать согласованность уже не только Markdown-файла, но и записи о его состоянии. Каталог может конфликтовать между параллельными PR. Запись может перестать соответствовать статье. Генератор может вести себя по-разному в разных окружениях. То есть зависимость от неполной Git history уменьшается, но вместо нее появляется новый объект, который тоже нужно корректно обновлять и переносить между ветками.

Это важный компромисс такого подхода: сохраненное состояние делает результат менее зависимым от окружения, но увеличивает количество состояния, за согласованность которого отвечает сама система.

Ретроспектива тоже требует границ достоверности

Одну версию решения полностью откатили через 21 минуту, а на следующий день тот же патч вернули. Эти два события подтверждаются историей изменений. А вот причина отката в репозитории не записана.

Поэтому при восстановлении эволюции решения я разделял то, что можно увидеть напрямую в diff и последовательности коммитов, и то, для чего история уже не дает ответа. Сам факт быстрого отката можно зафиксировать. Объяснять его конкретной технической причиной без дополнительного источника — уже было бы догадкой.

Для меня это хороший пример того, почему инженерную ретроспективу иногда приходится строить не как красивую историю с известной причиной каждого решения, а как набор подтверждаемых фактов с явно обозначенными пробелами.

В итоге изменился сам вопрос. Изначально он звучал как «как показать дату обновления статьи?», а стал звучать так: на основании чего система считает, что содержание статьи изменилось именно в эту дату?

И несколько строк вокруг git log перестают выглядеть очевидным решением.
